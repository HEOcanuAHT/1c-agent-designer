## #std737 — проверка в коде / UI

1. При большом числе ролей **не** настраивай видимость элементов формы по ролям (просмотр/редактирование реквизитов, пользовательская видимость, использование команд по ролям). Лучше:
   - отдельные формы при сильных различиях;
   - проверка прав в коде при небольших отличиях (учти влияние на скорость открытия формы).
2. Не настраивай ролевую видимость командного интерфейса / начальной страницы «по флажкам ролей» — давай права на разделы, общие формы и объекты.
3. Для прав на объекты метаданных в коде — **`ПравоДоступа`**, не `РольДоступна("ИмяРолиИзмененияСправочника")`.
4. Если роль — только маркер доп. права (без прав на метаданные) — `РольДоступна` / `Пользователи.РолиДоступны` (БСП), с учётом полных прав / привилегированного режима.
5. Не делай фиктивные права с RLS `ГДЕ ЛОЖЬ` ради проверки через `ПравоДоступа`, если данные реально читаются в привилегированном режиме — проверяй роль.

## RLS и производительность

См. также #std658 п.7 в `std-query-optimization`: разные RLS на одно право → скрытый `ИЛИ` в СУБД.

## Чеклист

- [ ] В коде — `ПравоДоступа` для прав на объекты
- [ ] Маркерные роли — через `РольДоступна` / БСП
- [ ] Нет роевой «видимости по флажкам» на формах при десятках ролей
- [ ] Нет конфликтующих RLS у одного пользователя на одно право
